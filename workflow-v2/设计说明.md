# workflow v2 设计说明

把 Goferret 的 `report.json` 变成给上游维护者的复现报告。目标是三个词：**简单、稳定、清晰**。

## 与旧版的对比

| | 旧版（`go_vuln_detect-检测代码/verify/`） | v2 |
|---|---|---|
| 步骤 | 8 阶段、10 个脚本、4 类证据文件 | 6 步、1 个 CLI、每步一个产物 |
| LLM 调用 | 项目信息、源码定位、测试设计、最终判定、对抗复核共 5 处，temperature 0.1 | **只有测试设计 1 处**，temperature 0，按输入哈希缓存 |
| 最终判定 | LLM 判定 + LLM 对抗复核 | **纯规则**：只看测试打印的固定标记和冻结的 `bug_if` 条件 |
| 结论标签 | 5 种结论 + A/B/C + E0–E4 + 3 种源码结论 + 4 种运行分类 + 4 种到达状态 + 5 种双臂状态 + 8 种差分结果 | **3 种**：已复现 / 不成立 / 未能复现 |
| 报告 | 每条 30–60 行、7 个章节 | 只写已复现的条目：位置、一句话、复现命令、预期输出、修复建议 |
| 项目假设 | 写死 filebrowser 的路由文件、容器名、仓库地址、TUS 提示词 | 无；证据只用函数源码 + AST 守卫链 + 调用点 |
| 环境 | 依赖预先启动的容器，未断网 | 每次一次性容器，`--network none`，模块缓存只读，镜像 digest 记入日志 |

## 六步

```
select → evidence → design → run → judge → report
 机械     机械      LLM×1    Docker   规则     渲染
```

1. **select**：单元 = (函数, 缺失步骤类别)，同单元多条发现合并。排序键固定：严重度 → 最高置信度 → 函数名 → 模板号；每仓库取前 N（默认 5）。测试辅助/示例路径不入选。`unit_id` 由函数名和类别哈希得出，与数组顺序无关。
2. **evidence**：按 `file:Recv.Name` 定位函数体；`ast_analyzer --guards` 抽守卫链；`grep` 找调用点并排序；附上检测器的主张（标明是待验证假设）。不含时间戳。
3. **design**（唯一的 LLM 步骤）：先在容器里确认目标包能编译（不能则记 `package_unbuildable`，不调 LLM）。输入 = evidence + `go doc -all -u` + 同包最相关的 2 个现有测试。输出一份两臂测试和一个机器可读的 `bug_if` 条件；只有编译失败才重试（把编译器输出和涉及符号的 `go doc` 送回），最多 3 轮。编译通过即冻结（`experiment_test.go` + `test.sha256` + `spec.json`），之后不再生成。
4. **run**：复制 T 版本源码到临时目录，写入冻结测试，`docker run --rm --network none … go test -run ^TestRepro_<id>$ -count=1 -v`，原始输出和镜像 digest 写入 `run.log`。
5. **judge**：每臂三行标记 `REACHED / RESULT / OBSERVED`。规则顺序：超时或构建失败 → 未能复现；缺标记 → 未能复现；benign 未到达 → 未能复现（前置条件未建立）；malicious 被已知守卫拦下且 benign 到达 → **不成立**；两臂 RESULT 没有数值/布尔差异 → 未能复现；`bug_if` 对 malicious 为真、对 benign 为假 → **已复现**；其余 → 未能复现。耗时、内存、临时路径、随机数一类的值不参与判定。
6. **report**：每仓库一份草稿。已复现的条目按三类分节：远程输入可触发 / 本地文件或内部数据触发（提示信任边界）/ 函数本身不做鉴权检查（提示上游可能有中间件）。附录一行一条列出其余单元及原因。不出现工具名、置信度、CVSS。

## 稳定性措施
- LLM 只在 design 出现，temperature 0，输入哈希缓存；冻结后重跑零调用。
- 判定输入不含任何随时间变化的字段；`RESULT` 中的耗时、临时路径等易变值被过滤。
- 容器一次性、断网、镜像 digest 固定；`check-stable` 再跑一遍 run+judge 逐单元比对。

## 首批 10 个小仓库的结果（2026-09-29）
- 51 个单元（含强制加入的 ffuf 真值单元）：已复现 8，不成立 0，未能复现 43（其中所在包无法编译 7、测试三轮未能编译 11、两臂无区分 9、前置条件未建立 6、超时 2、其他 8）。
- `check-stable`：51/51 单元两次运行结论与观察值完全一致。
- 真值验证：ffuf GO-2026-6369（gzip 解压炸弹）对应单元判为已复现，实验为 6MB gzip 响应体被完整读取、绕过 5MB 上限。
- 本轮 LLM 调用约 90 次（deepseek-v4-pro，全部命中缓存后重跑为 0 次）。

## 在已确认漏洞上的验证（cases_validation/）
用负责人此前已上报并被确认的 8 条 advisory（filebrowser/croc/harbor/alist）做回归验证：**7/8 advisory 至少一个目标函数被 workflow 自动复现，行为与 advisory 描述一致；36 个单元 check-stable 全部 0 差异。** 唯一未复现的 #6（harbor 中间件 fail-open）因所在包 TestMain 强依赖 Postgres、离线无法运行，如实标为 `package_needs_infra`。检测器当前开发版只报到 3/8 的目标函数——检出是短板，复现层用 `--manual` 绕开检测器独立衡量。详见 `cases_validation/README.md`。

这一轮为验证新增的通用能力：设计上下文追加"被调函数源码 + 相关测试的初始化片段"；新增 `package_needs_infra` 终态；判定新增"状态码压过 REACHED""拦截点在目标行后不算被拦""资源类实验须体现放大"等机械规则（全部无 LLM 判断）。

## 已知限制
- 同包单元测试看不到路由层和中间件，鉴权类主张只能证明"函数本身不检查"，报告已单独分节提示。
- `bug_if` 由 LLM 在设计时给出，冻结后稳定但不保证正确；报告把条件和实测值并列，便于维护者核对。
- 测试三轮编译失败的单元（约 20%）目前直接记为未能复现；提高轮次或改进 API 提示可以再降低。
