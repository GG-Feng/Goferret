# 证据标准与判断矩阵

## 1. 原则

本工作流把“工具发现了什么”和“团队证明了什么”分开记录：

- `report.json` 生成待验证主张。
- `project.md` 提供项目级事实与边界。
- `code.txt` 提供真实源码路径和缓解信息。
- `runtime.log` 提供受控运行行为。
- `report.md` 只根据三类人工证据形成结论。

## 2. 已验证的 JSON 字段

真实样例的顶层结构如下：

| 字段 | 类型 | 用途 | 能否作为最终证据 |
| --- | --- | --- | --- |
| `scan_info` | object | 项目标识、目标路径、模型、时间、函数覆盖和耗时 | 只作为来源元数据 |
| `project_domains` | array | 扫描器推断的项目安全领域 | 否，只用于阅读排序 |
| `summary` | object | 告警总数及严重度、领域、类别统计 | 否，只用于完整性检查和概览 |
| `findings` | array | 单条候选告警 | 否，是复现入口 |
| `function_scores` | array | 函数风险评分与启发式原因 | 否，只用于阅读排序 |

每条 finding 的字段：

| 字段 | 是否稳定存在 | 处理方式 |
| --- | --- | --- |
| `template_id` | 是 | 身份元组的一部分 |
| `pattern_name` | 是 | 记录扫描器主张名称 |
| `confidence` | 是 | 保留工具置信度，不替代人工置信度 |
| `severity` | 是 | 用于排序，最终严重度单独评估 |
| `missing_step_category` | 是 | 指导检查缺失的安全步骤 |
| `cwe_alignment` | 否 | 可以缺失或为 `null`，不得补造 CWE |
| `reasoning` | 是 | 待验证推理 |
| `evidence` | 是 | 扫描器截取的候选代码线索 |
| `function` | 是 | 文件与函数定位，可能没有精确行号 |

## 3. Finding 身份

源 JSON 没有独立稳定 ID。案例内按数组下标加一生成三位展示 ID：

```text
findings[0] -> F001
findings[1] -> F002
```

所有证据文件还必须记录身份元组：

```text
(template_id, pattern_name, function)
```

重新扫描后即使序号变化，也可以用 scan ID、JSON SHA-256 和身份元组定位原告警。不要只使用 `pattern_name`，因为同一模式可能命中多个函数。

## 4. 四文件证据包

### 4.1 `report.json`

要求：

- 保留原始内容，不手工修改。
- 记录 SHA-256。
- 验证 `summary.total_findings == findings.length`。
- 对 JSON 内的绝对路径、模型输出和代码摘录按敏感材料处理。

### 4.2 `project.md`

必须回答：

- 分析的是哪个仓库、commit、module 和 Go 版本。
- 报告扫描了多少函数，覆盖率限制是什么。
- 项目如何构建和运行，Docker 环境是什么。
- 关键入口、权限模型、默认配置和外部依赖是什么。
- 哪些输入是不受信任的，哪些只来自受信任内部组件。

### 4.3 `code.txt`

必须回答：

- 报告命中的函数是否真实存在。
- 真实入口和调用方是否可达。
- 关键输入从哪里来，谁能控制。
- 数据经过哪些转换、校验和权限检查。
- 危险操作和实际副作用在哪里。
- 是否存在调用方、标准库、配置或运行环境缓解。

代码片段必须包含路径、行号、commit 和上下文，不能只截取单行 sink。文件使用纯文本头部字段和分隔标签，不写分析性 Markdown；分析内容统一进入 `report.md`。

### 4.4 `runtime.log`

必须回答：

- 在什么容器、commit 和配置上运行。
- 执行了什么精确命令。
- 预期观察是什么。
- stdout/stderr 和退出码是什么。
- 输入是否到达真实代码路径。
- 被报告行为或缓解行为是否出现。
- 清理是否完成。

日志保持原始文本；关键片段可以被 `report.md` 引用，但不能替代日志文件。

## 5. 证据等级

| 等级 | 名称 | 内容 | 可以支持的结论 |
| --- | --- | --- | --- |
| E0 | 检测器线索 | JSON reasoning/evidence、领域、函数评分 | 只能建立候选 |
| E1 | 代码存在 | 目标 commit 中存在报告描述的函数或模式 | 只能说明代码形态存在 |
| E2 | 真实路径 | 调用方、输入来源、可控性、sink 和缓解层已闭环 | 支持设计运行实验 |
| E3 | 运行行为 | Docker/测试日志证明行为成立或被阻断 | 支持复现或误报判断 |
| E4 | 影响证明 | 运行结果证明实际安全边界或资源影响 | 支持已证明的影响范围 |

E0 不能单独进入最终结论。通常 `confirmed` 至少需要 E2 + E3；声称具体影响时需要 E4。

## 6. 判断矩阵

| 代码路径 | 可达/可控 | 运行日志 | 影响 | 结论 |
| --- | --- | --- | --- | --- |
| 存在 | 已证明 | 行为成立 | 已证明 | `confirmed` |
| 存在 | 只在明确前提下成立 | 行为成立 | 已证明或受限 | `conditional` |
| 存在 | 已证明或可测试 | 缓解稳定阻断 | 未发生 | `false-positive` |
| 与报告不一致 | 不成立 | 负向测试支持 | 未发生 | `false-positive` |
| 存在 | 未闭环 | 未观察到 | 未证明 | `not-reproduced` |
| 不完整或版本不一致 | 未知 | 无效/缺失 | 未知 | `insufficient-evidence` |

### 6.1 `confirmed`

只有真实入口、输入可控性、目标代码路径和运行行为形成闭环时使用。结论文字不得超过日志实际证明的范围。

### 6.2 `conditional`

行为已复现，但依赖非默认配置、特定平台、已有权限、特定版本或外部组件。必须在摘要和详细结论中都列出前置条件。

### 6.3 `false-positive`

需要正向反证，例如：

- 调用方在进入目标函数前拒绝恶意输入。
- 标准库稳定返回错误，危险操作没有发生。
- 权限或边界检查在真实路径上生效。
- 报告误解了类型、参数语义或数据来源。
- Docker 负向测试直接证明缓解层阻断行为。

仅仅“本次没复现”不够。

### 6.4 `not-reproduced`

实验本身有效，但没有观察到报告行为，同时也没有证明报告错误或缓解稳定存在。保留实验和日志，列出下一项最小补证步骤。

### 6.5 `insufficient-evidence`

适用于三文件缺失、commit 不一致、mock-only、不可达调用方、日志无退出码、测试未命中真实路径或影响只停留在理论描述。

## 7. 一致性检查

每条 finding 在四个位置必须一致：

| 项目 | JSON / intake | `code.txt` | `runtime.log` | `report.md` |
| --- | --- | --- | --- | --- |
| scan ID | 必须 | 必须 | 必须 | 必须 |
| finding ID | 必须 | 必须 | 必须 | 必须 |
| 身份元组 | 必须 | 必须 | 必须 | 必须 |
| commit | intake 可记录 | 必须 | 必须 | 必须 |
| 结论 | 无 | 源码阶段结论 | 运行结果 | 最终判断 |

发现错配时停止判断，不把一个 finding 的代码或日志用于另一个 finding。

## 8. 日志与敏感信息

提交协作仓库前检查并脱敏：

- 访问令牌、Cookie、私钥、数据库密码和云凭据。
- 私有仓库 URL、内部主机名、个人目录和用户名。
- 未公开漏洞的完整利用载荷或容易被直接滥用的操作细节。
- 第三方个人数据和生产数据。

需要保留原始敏感证据时，将其放在经批准的受限存储中，在 `report.md` 只写证据索引和脱敏摘要。
