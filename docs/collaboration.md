# GitHub 协作方式

## 仓库使用方式

建议把每个复现任务作为一个 Issue 或一个独立 Markdown 文件管理。若任务需要多人修改，推荐使用 Pull Request 进行复核。

## 分支建议

| 分支 | 用途 |
| --- | --- |
| `main` | 稳定版本，只放已复核的工作流和结论。 |
| `case/<short-name>` | 单个复现任务或案例。 |
| `docs/<short-name>` | 工作流文档调整。 |

## Pull Request 检查清单

提交复现或判断结论前，检查：

- 是否说明问题背景。
- 是否记录环境和版本。
- 是否记录每次复现尝试。
- 是否有证据支持结论。
- 是否区分事实、推断和建议。
- 是否去除了敏感信息。

## Issue 标签建议

| 标签 | 含义 |
| --- | --- |
| `intake` | 等待澄清或补充材料。 |
| `reproduction` | 正在复现。 |
| `judgement` | 正在判断。 |
| `needs-evidence` | 证据不足。 |
| `needs-review` | 等待合作者复核。 |
| `resolved` | 已处理完成。 |

## 敏感信息处理

不要提交：

- 密码、令牌、Cookie、密钥。
- 用户个人信息。
- 未脱敏的生产数据。
- 内部系统不可公开链接。
- 违反许可的数据、图片、论文或代码。

可以提交：

- 脱敏样例。
- 聚合统计。
- 截断日志。
- 本地可生成的模拟数据。
- 指向私有系统的占位说明。

## 合作者加入方式

仓库创建为 private 后，可以在 GitHub 仓库页面进入：

`Settings -> Collaborators and teams -> Add people`

添加合作者后，建议先给 `Read` 或 `Triage` 权限。如果对方需要直接修改文档，再升级到 `Write` 权限。
