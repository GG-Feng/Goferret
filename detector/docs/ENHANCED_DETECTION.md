# 增强检测实现与验证边界

## 流程

`--detection-mode enhanced` 保留原有发现通道，并加入独立的全文语义发现。新通道不受既有 G1、角色、入口、sink 表或行为链模板筛选影响。模型从包概览和分块源码提出安全假设，再由新的调查会话核验，源码片段由程序核对。

`enhanced_detection.py` 管理源码快照、上下文工具、发现与核验；`ast_analyzer/source_index.go` 输出 AST 声明/函数/闭包位置及排除、解析错误；`detect_vulns.py` 负责与旧通道衔接。未改用 OCR 运行时或复制其源码，不依赖旁边的 OCR 仓库。

增强报告中的 `findings` 包含 supported 和 unknown；`enhanced.triage_queue` 另给出适合人工调查的紧凑视图。`needs_review` 表示已发现并保留候选，但尚不能判为源码支持；候选的位置、原文引用、核验失败原因和未决问题均可直接查看。发现阶段还检查阻断/拒绝路径是否错误返回成功状态或可用答案，这类协议语义问题不依赖传统危险 API。

## 保护假设

增强分析保留净化函数的输入根以及带 limiter 的输入流，不把 Content-Type/范围比较/校验正则的存在直接等同于保护成立。已有来源、sink 与校验信息送入候选核验；规则通道中缺少语义提取结果的事实仍能被保留。多处危险位置不再被 R2 的同类别裁剪或 X4 的同函数类别去重隐藏。

调查重点是输入控制、调用关系、检查对象、返回值处理、失败分支、赋值覆盖和授权入口。结构化原候选中的“无检查”等旧文字仅为假设，核验提示明确禁止当成事实。

## 来源与输出约束

- 模型调用沿用当前配置，以 JSON action 请求白名单工具，不执行模型提供的 shell 命令。
- 快照仅包含被枚举的生产 Go 文件，忽略测试、生成代码、vendor/node_modules/testdata/.git 和符号链接；工具只能查询快照。配置文件、依赖源码和外部仓库不在本轮自动查询范围内，相关前置条件不足时应保持 unknown。
- read_function/read_lines 有行数和字符上限；search_symbol/get_callers/get_callees 返回截断状态。调用图沿用有界、流不敏感和名称分派分析，未引入完整 go/types/SSA。多实现与未解析关系不能当成唯一确定路径。
- get_callers/get_callees 的每条边现在附带快照校验过的调用点原文、调用方参数、实参来源，以及最多 20 个候选目标的参数与返回值根；无法引用的调用点留空，截断和歧义均显式标记。这些事实帮助模型沿调用边调查，不证明运行时一定走到该目标。
- find_field_uses(field,path_prefix,type_id) 在 AST 索引的生产 Go 源码中查找字段的选择器读取、赋值写入及带键字面量，返回原文行、函数 ID、最多 100 项及截断信息。可选 type_id 按显式包路径和结构体类型过滤；直接写出的跨包类型和函数参数类型可以连接，如 `module/protocol.RequestMessage`。未显式解析的用法没有 type_id，不会被强行归入某个类型。局部标识符作为字段值时，结果按 Go AST 的变量绑定身份和源码位置列出此前的可能赋值，避免把同名内层变量的赋值混入。此索引没有 go/types/SSA：别名、接口、嵌套字段及分支路径仍可能歧义，可能赋值不等于实际运行时来源。
- 文件全部进入声明边界拆分；大型函数继续按行拆分。单行超过字符限额时标记任务失败并使报告 partial，不宣称完整检查。
- 语义提取响应按函数 ID 绑定；重复、未知 ID 拒收，缺失及格式错误显式记录。发现响应必须回传当前 unit_id。语义候选的首条危险操作引文必须精确对应源码；次要引文不符时丢弃该引文并留下 `reference_warnings`，候选继续接受独立核验。首条引文不符的候选保存在 `invalid_candidates`，使运行 partial。
- supported 至少要求 input、operation、impact 三类带真实源码引用的主张，operation 必须指向候选危险位置，且没有未决条件。refuted 至少要求 protection 或 contradiction 证据，且没有未决条件。
- 当前 refuted 还要求一条 operation 主张引用候选危险位置；只引用某处存在保护函数不足以驳回该候选。模型仍需判断保护是否作用于同一输入路径，程序不能仅凭位置证明这一语义关系。
- 模型只需提供引用的文件和行号，程序从当前源码快照回填准确原文；若模型仍显式提供引文，程序核对文件、行号与内容，仅允许省略行首空白，其他差异会拒收。发现候选的操作引用若唯一落在另一已索引函数内，程序重绑定函数 ID 并记录原 ID 和原因；歧义位置仍拒收。程序不具备自动证明自然语言主张为真的能力；核验仍依赖模型，需独立质量评估。
- DeepSeek 请求启用 JSON 对象响应格式，减少发现及核验阶段的非 JSON 输出；HTTP 200 本身不代表任务完成，仍需检查报告任务状态和候选引用有效性。
- finding ID 合并仍采用函数、危险位置、类别和输入路径；语义假设不同则保留。额外的 investigation_groups 按函数、危险位置行和类别把候选放入同一调查队列，先核验每组代表、再处理其他成员。它不是已证明相同的安全根因，代表结论不会复制给其他成员，全部 raw_candidates 仍保留。

## 兼容及成本

旧模式保持默认和报告结构。增强报告添加 schema_version 和 enhanced；新类别采用 other_security，新语义结果 CVSS/confidence 为空。测试生成器可回退读取旧 finding ID，新增报告使用统一 finding ID。

每个发现单元及每个候选最多六轮模型请求，每轮最多三个查询。新增通道使用现有调用日志及用量统计，不实现全局 token 硬预算、缓存复用或断点恢复。原有通道仍使用原有重试策略。上下文轨迹与报告可能较大，应将结果当作含目标源码的本地产物。

新增 `--enhanced-max-model-calls N` 为增强发现和核验共享的逻辑请求数上限，`0` 表示不限；每轮请求前扣额。预算耗尽后未开始的源码单元是 `pending`，未核验的候选是 `unknown`，报告标为 `partial`，`enhanced.limits` 记录上限、总使用量及发现/核验各自的调用数。这个上限不覆盖先运行的原有结构化检测，也不是 token、费用或全流程请求硬上限。

每个源码单元发现后至多给一个新调查组的代表候选一轮核验；之后继续下一个单元。发现阶段结束后，尚未调查的组代表先获得请求，再按轮次轮流继续；组内其他成员随后独立核验。同一 finding ID 不会重复开启调查，续轮继承已有查询轨迹。有限额度下，未扫描单元明确标为 `pending`；候选未完成核验则为 `unknown`。这个调度减少单个候选连续占用额度，但不保证有限额度覆盖所有源码和候选。语义提取提示使用 `function_id`，旧响应的 `function` 字段仅在精确匹配请求 ID 时兼容，不按返回顺序猜测函数身份。

发现和核验提示现在明确要求检查 Go 代码中的真实输入边界、保护失败分支、检查后改写、路径及符号链接、URL 重定向、资源扩张前的限制，以及路由和中间件覆盖；跨函数值传递还要查看调用参数、返回值与消费者。转发 URL 路径时需区分解码后的 Path 与 EscapedPath/RawPath，并用字段查询检查协议字段的两端。这些是调查问题，不能凭提示词或模式命中直接宣称漏洞成立。

## 验证口径

本轮自动化使用真实 Go AST 与模型替身，覆盖：

- 全文件分块、闭包、泛型、声明、解析失败及排除记录；
- 输出 ID 乱序、缺失、重复、未知、错误引用、越界查询；
- 跨包调用方查询与净化输入根保留；
- 显式类型字段跨包匹配、同名字段与内外层同名变量隔离、同一行赋值来源；
- 无 AST sink/入口时仍可走新发现通道；
- R1 日志检查与 return 检查均先生成候选，后接受核验结果；
- X4 语义提取失败时保留候选，多处 R2 危险位置保留；
- 查询预算耗尽、模型失败、错误裁决和中断状态；
- 完整 CLI 报告与生成文件 ID。

原有七组 selftest 用新构建分析器验证兼容。`openhole` 的实际模型已知位置回归记录见 [实验报告](../.planning/openhole-smoke-20261008/report.md)：两版均未产生与编码路径补丁根因准确对应且完成核验的候选，报告为 `partial`。尚无 Docker 复现，不给出精确率、召回率提升结论。
